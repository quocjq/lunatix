* Naming note

The user's informal term "unflake" refers to the pattern documented by Den as *no-flake*. Where the guide references upstream, it uses Den's official name. Where it describes the local migration, either term is fine.

* TL;DR

Replace the auto-generated =flake.nix= (currently regenerated by =github:denful/flake-file= from =flake-file.inputs.*= declarations scattered across modules) with a hand-written =default.nix= of the [[https://github.com/vic/vix][vix]] shape:

#+BEGIN_SRC nix
let
  sources = import ./npins;          # produced by `npins`
  with-inputs = import sources.with-inputs sources (import ./follows.nix);
  outputs = inputs:
    inputs.flake-parts.lib.mkFlake { inherit inputs; }
      (inputs.import-tree ./modules);
in with-inputs outputs
#+END_SRC

Pinned revisions move from =flake.lock= to =npins/sources.json=; follows move from the inline =inputs.X.inputs.Y.follows= block in =flake.nix= to =follows.nix=. =flake.nix= itself survives as a thin shim (={ outputs = _: import ./.; }=) so anyone still typing =nix build .#igloo= keeps working.

* When to use this guide

You are maintaining Lunatix on a single NixOS host (=/home/lunixose/Proj/lunatix/=, host =igloo=, =x86_64-linux=, user =lunixose=), you already use Den as your module system, and you are comfortable running commands that touch =flake.lock=. You want pins to live in a normal text file you can diff, and you are willing to give up =nix flake update= ergonomics.

* When NOT to use this guide

- The repo has fewer than five inputs and a single host. The indirection is not worth it.
- You rely on =--override-input= for ad-hoc experimentation. No-flake supports overrides only via =npins update= plus a rebuild, not as a CLI flag.
- You want every consumer (CI, =nixos-rebuild=, IDE plugins, direnv) to keep using the =flake:= URL scheme as today. The shim covers most of this, but some tools introspect =flake.lock= directly.
- You are on Nix < 2.18 stable. The =with-inputs= pattern works on stable, but =nix build --file . -A= requires a fairly recent =nix-build=. Use =nix-build -A ...= if you are pinned to an older Nix.
- You are starting a new project. Use =nix flake init -t github:denful/den#noflake= (or copy [[https://github.com/denful/den/tree/main/templates/noflake][den/templates/noflake]]) and skip this guide.

* Rationale                                                           :rationale:

Den's no-flake template is, conceptually, what flakes would have been if =flake.lock= had been a Nix expression instead of a JSON document. =flake.nix= becomes a two-line shim or disappears entirely; pins live in a plain =npins/sources.json= managed by the [[https://github.com/andir/npins][npins]] CLI; follows live in a plain =follows.nix=. The whole inputs attrset is then assembled by the tiny =with-inputs= helper from [[https://github.com/vic/vix][vic/vix]].

** What no-flake buys you

The headline benefit is that pins become editable Nix code. =npins/sources.nix= is a literal attrset of =name -> { type, url, hash, ... }=, so =git diff= shows the exact change (URL, hash, branch), and code review can comment on individual pins. =flake.lock=, by contrast, is JSON-with-comments-not-allowed and ~50 KB of nested =original=/=locked=/=dir= triples that nobody reads.

The second benefit is operational: =npins= is a single binary with no daemon, no fetchers registry, no flake CLI. It works on Nix 2.18 stable without =--extra-experimental-features 'nix-command flakes'=. The =with-inputs= library that consumes =sources.nix= is also pure Nix — no flake-parts required. So the entire pin pipeline runs in environments where flakes are deliberately disabled (NixOS installers, recovery shells, =nix-shell -p=).

The third benefit, specific to this repo, is that *flake-file stays as the input aggregator, but its output target shifts from =flake.nix= to =npins/sources.json=*. Lunatix currently has =flake-file= as a flake input that consumes =flake-file.inputs.*= declarations from at least nine module files (see [[#current-state][Current state]]). Each declaration is a side-channel for "this module secretly needs a flake input". The [[https://github.com/vic/vix/tree/unflake][vix unflake pattern]] preserves this aggregator role: modules still declare inputs as Nix module options, but =write-npins= (instead of =write-flake=) emits =npins/sources.json=, and =with-inputs= reads that. This is the canonical Dendritic pattern — modules declare *what they need*, the aggregator collects, the resolver (with-inputs) feeds them into the eval.

The fourth benefit is decoupling. Den philosophy: /Den does not replace NixOS, home-manager, or flake-parts — it sits on top of them and generates the same flake outputs you are used to./ With no-flake, the resolver and the module composer are separate concerns. You can swap =npins= for the canonical [[https://codeberg.org/goldstein/unflake][goldstein/unflake]] resolver (=unflake.nix=) without touching =default.nix='s module assembly, and vice versa.

** What you lose

You lose =nix flake update=, =nix flake lock --update-input <name>=, and =--override-input=. Updates become =npins update nixpkgs= (or just =npins update= for everything). Overrides are awkward — you can edit =sources.nix= directly, but =npins= will rewrite it on the next update, so overrides belong in a separate working copy or in an overlay in your =default.nix=. Most Lunatix builds do not need overrides, but CI pipelines that pin to a specific commit during a regression bisect will need a workaround.

You also lose the ability for downstream consumers to treat your repo as a flake URL (=github:lunixose/lunatix=). The =flake.nix= shim keeps the local =nix build .#igloo= path working, but =nixos-rebuild --flake github:lunixose/lunatix= does not work — it would have to clone the repo, and the cloned =default.nix= needs =npins= and the network to resolve =sources.nix=. The current =justfile= already avoids remote-flake usage (--=.#igloo=), so this is not an immediate loss, but it constrains future hosting.

You also lose flake-parts' per-system iteration as a first-class concept. =flake-parts.lib.mkFlake='s =perSystem= is replaced by the module system iterating over =den.hosts.<system>.<host>= and assembling configurations. The =flake-parts= /library/ can still be used (vix's pattern); what you lose is the CLI-shaped iteration that the flake evaluator provided.

** Why Lunatix specifically benefits

Lunatix is already 90% Den. =modules/flake/dendritic.nix= loads =den.flakeModules.dendritic= and =flake-file.flakeModules.dendritic=. =modules/flake/defaults.nix= sets =den.default.nixos.system.stateVersion= and pulls in =den.aspects.settings=, =den.batteries.hostname=, =den.batteries.user-shell "bash"=. Every =lunix/*.nix= module is a Den module. The flake is essentially a delivery vehicle for Den. Replacing it with a no-flake template that is also Den-native is a closer fit than keeping flake-parts around as scaffolding.

The flake-parts wrapper is only there because the flake has to expose something under =outputs=. In no-flake, the equivalent is =(inputs.nixpkgs.lib.evalModules { ... }).config= — you evaluate the same Den module tree, and the resulting attrset is your flake outputs. The Den authors [[https://den.denful.dev/tutorials/noflake/][documented this exact switch]] and ship =with-inputs= to make it painless.

The single-host profile (=x86_64-linux.igloo=, user =lunixose=) means there is no multi-system complexity to model. The current flake's =flake-parts.lib.mkFlake= is being used as a generic module assembler, not as a per-system iterator.

** Trade-offs worth thinking through

*** Vendoring

Today, =flake-file= is a flake input, which means =nix flake update= bumps it automatically. With no-flake, =flake-file= stays as the input aggregator (its role is unchanged) but =flake-file.inputs.*= declarations now flow into =npins/sources.json= via =write-npins= instead of into =flake.nix= via =write-flake=. There is no upstream to bump — =flake-file= is loaded like any other input, =with-inputs= reads its outputs.

*** Transitive input complexity

The current flake has 19 top-level inputs and =flake.lock= records 88 non-root nodes. Many of those 88 are pulled in transitively (e.g., =nixpkgs-lib= from =flake-parts=, =nixpkgs= from =home-manager= even though =home-manager.inputs.nixpkgs.follows = "nixpkgs"= is set). When you switch to =sources.nix=, transitive inputs are no longer pinned in a =flake.lock= — they are resolved at evaluation time against whichever =nixpkgs= your direct =nixpkgs= input pins. In practice this is fine because =npins= lets you pin direct inputs only, and follows propagate correctly.

*** Learning curve

Anyone who clones the repo has to install =npins= before they can build. =justfile= recipes can wrap this (a =bootstrap= recipe should run =nix run .#write-npins=), but the failure mode is silent — =nix build .#igloo= on a fresh checkout fails with a confusing =default.nix= error if =npins= was never populated. The =bootstrap= recipe in [[#commands][Commands]] adds a guard.

*** Lockfile ownership

In a flake, =flake.lock= is the lockfile and =flake.nix= references it implicitly. In no-flake, the lockfile is =npins/sources.json= (or =unflake.nix=, if you adopt the goldstein resolver). =flake.lock= either disappears or becomes a regenerated artefact for tools that still read it. This is a workflow change, not a code change, but it affects every contributor's mental model.

** When NOT to migrate

If your flake has fewer than five inputs, or if your team relies on =--override-input= for day-to-day work, the trade-off is not worth it. The =with-inputs= + =npins= pipeline is a small but real maintenance burden, and a vanilla flake-parts flake is fine for those cases. The guide is written for repos like Lunatix — Den-heavy, single host, multiple cross-cutting flake-file inputs — where the alignment with Den philosophy is the deciding factor.

** Resolver choice: npins vs unflake

Two resolvers exist in the Den/no-flake ecosystem:

- [[https://github.com/andir/npins][npins]] + [[https://github.com/denful/with-inputs][with-inputs]]: the most documented path. =sources.json= is JSON; =with-inputs.nix= reads it. vix uses this. This guide picks npins.
- [[https://codeberg.org/goldstein/unflake][goldstein/unflake]]: a single binary that reads =inputs.nix= and writes =unflake.nix= (a generated Nix expression that doubles as the lockfile). Slightly fewer moving parts; less community documentation. Compatible — switching back is editing =default.nix=.

Either is fine. The guide picks npins because the Den tutorial uses npins, vix uses npins, and the operator ergonomics (separate =update= and =add= subcommands) match what most Nix users expect.

** Step 3 — Populate sources.json from the existing flake.lock

There is no built-in =npins import-from-lockfile=, so we use a one-shot Nix script that reads =flake.lock= and writes =npins/sources.json=. Save this as =/tmp/import-from-lock.nix=:

#+BEGIN_SRC nix
let
  lock = builtins.fromJSON (builtins.readFile ./flake.lock);
  toPin = name: node:
    if node.locked.type == "github" then {
      inherit name;
      type = "GitHub";
      repository = node.locked.owner + "/" + node.locked.repo;
      revision = node.locked.rev or node.locked.ref or "";
      url = "https://github.com/${node.locked.owner}/${node.locked.repo}";
    } else if node.locked.type == "tarball" || node.original.type == "tarball" then {
      inherit name;
      type = "Tarball";
      url = node.original.url;
      hash = node.locked.narHash or "";
    } else null;
  pins = builtins.filter (p: p != null)
    (map (n: toPin n lock.nodes.${n}) (builtins.attrNames lock.nodes));
in {
  version = 1;
  pins = builtins.listToAttrs (map (p: { name = p.name; value = builtins.removeAttrs p ["name"]; }) pins);
}
#+END_SRC

Run:

#+BEGIN_SRC sh
nix-instantiate --eval --strict --json /tmp/import-from-lock.nix > /home/lunixose/Proj/lunatix/npins/sources.json
#+END_SRC

Then regenerate the Nix expression:

#+BEGIN_SRC sh
npins update --hide-warning
#+END_SRC

*Verify:* =cat npins/sources.nix= lists 20 top-level inputs (matching =flake.nix= lines 6–69). The transitive nodes (88 total in =flake.lock=) are not in =sources.nix= and that is correct — =npins= only tracks direct pins.

*** Special cases

- =nixpkgs= is pinned via tarball URL (=flake.nix= line 49), so its =sources.nix= entry will be ~{ type = "Tarball"; url = "https://channels.nixos.org/nixpkgs-unstable/nixexprs.tar.xz"; hash = "sha256-..."; }~. =npins update nixpkgs= will re-fetch the tarball and refresh the hash.

- Transitive inputs (=flake-parts_2=, =nixpkgs_2=, etc.) are intentionally skipped.

** Step 4 — Generate follows.nix

=follows.nix= mirrors the =inputs.X.inputs.Y.follows= block of =flake.nix=. The shape uses the *spec* format expected by [[https://github.com/denful/with-inputs][with-inputs]] — each top-level entry must have an =inputs= subkey (with the =Y.follows = "Z"= shape), or =follows.nix= will be silently ignored and the underlying flake's default follows will be used:

#+BEGIN_SRC nix
{
  # Each entry: { inputs.Y.follows = "Z"; } or { inputs = { Y.follows = "Z"; }; }
  # The bare { Y = "Z"; } shape is NOT a spec — with-inputs will treat it as a
  # raw value and your follows will be lost.

  # Inputs that follow extra inputs besides nixpkgs:
  agenix = {
    inputs = {
      nixpkgs.follows = "nixpkgs";
      home-manager.follows = "home-manager";
    };
  };
  flake-parts = {
    inputs.nixpkgs-lib.follows = "nixpkgs";
  };
  plasma-manager = {
    inputs = {
      nixpkgs.follows = "nixpkgs";
      home-manager.follows = "home-manager";
    };
  };

  # Inputs that explicitly do NOT follow nixpkgs:
  nix-doom-emacs-unstraightened = {
    inputs.nixpkgs.follows = "";
  };
}
#+END_SRC

The conversion rule: every =inputs.X.inputs.Y.follows = "Z"= in =flake.nix= becomes ~"X" = { inputs.Y.follows = "Z"; };~ in =follows.nix=. Empty follows (=''=) become ~{ inputs.Y.follows = ""; }~ to signal "do not follow". The bare ={ Y = "Z"; }= shape (without an =inputs= subkey) is silently ignored by =with-inputs= — easy mistake.

Save the file at =/home/lunixose/Proj/lunatix/follows.nix=. The rest of the inputs default to following the root =nixpkgs= and do not need entries. Refer to =flake.nix= lines 6–69 for the source-of-truth follows block.

*Verify:* ~nix-instantiate --eval --strict --json -E 'builtins.attrNames (import /home/lunixose/Proj/lunatix/follows.nix)'~ prints a JSON list of input names. Spot-check against the follows block in =flake.nix=.

** Step 5 — Create default.nix (flake-parts retained)

This is the canonical =default.nix=. It uses =flake-parts= so the existing modules under =modules/flake/= keep working unchanged.

#+BEGIN_SRC nix
# /home/lunixose/Proj/lunatix/default.nix
let
  sources = import ./npins;          # generated by `npins`
  follows = import ./follows.nix;    # hand-edited
  with-inputs = import sources.with-inputs sources follows;
  outputs = inputs:
    inputs.flake-parts.lib.mkFlake { inherit inputs; }
      (inputs.import-tree ./modules);
in with-inputs outputs
#+END_SRC

The =with-inputs= library is itself sourced from one of the pinned inputs (=sources.with-inputs=), so it is fetched and locked the same way everything else is.

*Verify:* ~nix-build -A flake.nixosConfigurations.igloo.config.system.build.toplevel~ builds the system. The path should match ~readlink result~ from before the migration.

** Step 6 — Add a no-flake-pure alternative (mention only)

If you want to drop =flake-parts= entirely and use raw =evalModules=:

#+BEGIN_SRC nix
let
  sources = import ./npins;
  follows = import ./follows.nix;
  with-inputs = import sources.with-inputs sources follows;
  outputs = inputs:
    (inputs.nixpkgs.lib.evalModules {
      modules = [ (inputs.import-tree ./modules) ];
      specialArgs = { inherit inputs; inherit (inputs) self; };
    }).config;
in with-inputs outputs
#+END_SRC

This is what the upstream [[https://den.denful.dev/tutorials/noflake/][Den tutorial]] recommends. It requires removing =inputs.flake-parts.lib.mkFlake= wrappers and switching to =inputs.nixpkgs.lib.evalModules= semantics. For Lunatix, =flake-parts= is still used by =modules/flake/= modules via =perSystem= and =mkFlake=-style integration, so *step 5 is the pragmatic choice*. Step 6 is a future cleanup.

*Verify (if attempted):* the same ~nix-build -A flake.nixosConfigurations.igloo.config.system.build.toplevel~ succeeds.

** Step 7 — Convert flake.nix to a generated shim

The new =flake.nix= is hand-written, not auto-generated:

#+BEGIN_SRC nix
# /home/lunixose/Proj/lunatix/flake.nix
# Thin shim that delegates to default.nix.
# Regenerate npins with `npins update`; do not edit inputs.* here.
{
  outputs = _: import ./.;
}
#+END_SRC

Add a Makefile target that writes a more elaborate transient =flake.nix= from =default.nix= for users who want to keep using the full flake CLI:

#+BEGIN_SRC makefile
# /home/lunixose/Proj/lunatix/Makefile
flake-from-default:
	@echo '{ outputs = _: import ./.; }' > flake.nix
#+END_SRC

Or, more aggressively, you can write a real =flake.nix= that re-exports =default.nix= outputs as flake outputs (so =nix flake show= works the same):

#+BEGIN_SRC nix
# flake.nix (hand-written, no flake-file)
let
  sources = import ./npins;
  follows = import ./follows.nix;
  with-inputs = import sources.with-inputs sources follows;
  outputs = inputs: import ./. inputs;
in { outputs = outputs; }
#+END_SRC

*Verify:* =nix flake check= passes. =nix flake show= lists =nixosConfigurations.igloo=. =nix build .#igloo= works.

** Step 8 — Switch flake-file output to npins

flake-file stays as the input-declaration aggregator, but its output target changes from =flake.nix= to =npins/sources.json=. This is the [[https://github.com/vic/vix/tree/unflake][vix unflake pattern]]: modules declare inputs as Nix module options under =flake-file.inputs.X.url = "github:..."=, flake-file aggregates them across the module tree, and =write-npins= emits =npins/sources.json=.

*Why keep flake-file:* Dendritic pattern means modules declare *what they need*, not *how to fetch it*. The aggregator (flake-file) lives at the wiring layer; the actual config modules stay pure-Nix. Dropping flake-file would force every module to declare pins directly, breaking the separation.

Steps:

1. Verify flake-file's npins writer is available:
   #+BEGIN_SRC sh
   nix run .#write-lock          # or nix run .#write-npins directly
   #+END_SRC
   First run will create =npins/sources.json= if missing — that's expected.

2. Inspect the result:
   #+BEGIN_SRC sh
   cat npins/sources.json | jq '.pins | keys'
   #+END_SRC
   Should list 20 input names matching the =flake-file.inputs.*= declarations.

3. The =flake-file.inputs.*= blocks in =modules/flake/dendritic.nix= and =modules/lunix/*.nix= stay as the *source of truth* for input URLs and follows. Edit them in modules, then re-run =write-npins= to refresh =npins/sources.json=.

4. The =flake.nix= shim from [[#step-7--convert-flakenix-to-a-generated-shim][step 7]] stays as a hand-written file. flake-file no longer regenerates it.

5. Add a =justfile= recipe for the workflow:
   #+BEGIN_SRC just
   update:
       nix run .#write-npins
       # Regenerate flake.lock if downstream tools need it:
       nix flake lock
   #+END_SRC

6. Remove the auto-generation marker from the old =flake.nix= (step 7 already replaced it with the shim). Delete the =write-flake= recipe from =justfile= if it exists.

*Verify:* =just build= succeeds. =nix flake check= passes. =npins/sources.json= has 20 pins. The =flake-file.inputs.*= blocks in modules are unchanged.

** Step 9 — Retire flake.lock

The lockfile no longer reflects the source of truth. Two options:

- *Option A (recommended)*: delete =flake.lock= from git, regenerate on demand via =nix flake lock= against the shim. The shim is just =import .=, so =nix flake lock= resolves inputs identically to =nix-build=.
- *Option B*: keep =flake.lock= for tools that introspect it (e.g., direnv's =use flake=). Update CI to regenerate it from =npins= sources via =npins update && nix flake lock=.

For Lunatix, *option A is cleaner* — the =justfile= already has an =update= recipe, and =npins update= followed by =nix flake lock= (only if a tool needs the lock) is the new flow.

*Verify:* ~git log --diff-filter=D -- flake.lock~ shows the deletion commit.

** Step 10 — Update CI and docs

- =README.md= line 99 ("The flake file is generated by =flake-file=...") becomes "The flake file is a thin shim around =default.nix=. Pin declarations live in modules under =flake-file.inputs.*=; refresh with =nix run .#write-npins= (=write-lock= auto-dispatches)."
- =justfile=:
  - =write-flake= recipe (line 57–58) is removed.
  - =update= recipe (line 61–62) becomes ~nix run .#write-npins~.
  - =build= / =switch= / =vm= recipes (lines 45–54) keep their =nix run .#igloo= form — the shim preserves it.
  - =bootstrap= recipe gains a guard: ~[ -f npins/sources.json ] || nix run .#write-npins~.
- =.github/workflows/*.yml= (if any): replace =nix flake update= with ~nix run .#write-npins~; replace =nix flake check= with ~nix-build -A flake.checks.x86_64-linux.igloo~.

*Verify:* =just --list= shows the updated recipes. =just build= succeeds. [[#verify][Verify]] walks the full end-state equivalence check.

* Parallel strategy                                            :parallel-strategy:

The migration runs while the existing flake keeps working. The trick is that =flake.nix= becomes a thin shim that delegates to =default.nix=, so =nix flake *= and =nix build .#igloo= both work, but only one file is the source of truth at any moment.

** Phase boundaries

- *Before step 5* (no =default.nix= yet): flake is the only source of truth. =flake.nix= is the auto-generated file from =flake-file=. Builds use =nix build .#igloo=.
- *Between step 5 and step 7* (both files exist): =default.nix= is the canonical source of truth. =flake.nix= is still the auto-generated file from =flake-file=. Builds can use either — ~nix-build -A flake.nixosConfigurations.igloo.config.system.build.toplevel~ (uses =default.nix=) or =nix build .#igloo= (uses =flake.nix=). To prevent drift, run =just build= after every change to either and confirm the resulting =/nix/store/...-nixos-system-...= path is identical.
- *After step 7* (=flake.nix= is a shim): =default.nix= is the only file with logic. =flake.nix= is a 1-line shim that does =import .=. Builds via =nix build .#igloo= and =nix-build -A ...= are now functionally identical because the shim delegates.
- *After step 8* (flake-file redirected to =write-npins=): =flake-file.inputs.*= declarations in modules are still the source of truth for input URLs and follows. flake-file now writes =npins/sources.json= instead of =flake.nix=. The hand-written shim from step 7 is =flake.nix=.
- *After step 9* (=flake.lock= deleted): the lockfile is regenerated on demand. The git diff is small.

** Why the shim works

The [[https://github.com/vic/vix/blob/main/flake.nix][vix pattern]] is ~{ outputs = _: import ./.; }~. When =nix flake check= or =nix build .#igloo= runs against this shim, Nix evaluates =default.nix= with the standard flake =inputs= attrset. The result is an attrset with =nixosConfigurations.igloo=, which is exactly what flake consumers expect. So =nix flake show=, =nix flake check=, and =nix build .#igloo= all work.

The shim does *not* make =nixos-rebuild --flake github:lunixose/lunatix= work — that requires resolving =sources.nix= (via =npins=) and =follows.nix= on the remote. The =justfile= already uses local flake references, so this is not a regression.

** Optional: regenerate flake.lock from npins

If a downstream tool requires =flake.lock= (e.g., direnv's =use flake=):

#+BEGIN_SRC sh
npins update
nix flake lock                 # regenerates flake.lock from the shim
#+END_SRC

This produces a =flake.lock= whose =nodes= are identical in shape to the one before migration — the =original.url= and =locked.rev= are read from =sources.nix= by =with-inputs=.

** Run order during the migration window

#+BEGIN_SRC sh
# 1. Edit a flake-file.inputs.* declaration   (e.g. in modules/flake/dendritic.nix, step 8)
# 2. nix run .#write-npins                     (regenerate npins/sources.json)
# 3. Edit follows.nix                          (if any follows changed)
# 4. just build                                (verify default.nix path)
# 5. cp flake.nix flake.nix.bak                (snapshot pre-shim)
# 6. Write new flake.nix shim                  (step 7)
# 7. nix flake check                           (verify shim)
# 8. diff <(readlink result) <(readlink result.bak)   # paths match
# 9. git add -A && git commit -m "migrate to no-flake"
#+END_SRC

Step 8 is the regression bar — if the resulting store paths differ, the migration is incomplete.

** Cleanup of flake-file consumers

The =flake-file.inputs.*= blocks in =modules/lunix/plasma.nix=, =modules/lunix/hyprland/hyprland.nix=, etc. become inert after step 8. They are not removed automatically because they are spread across many files and the cleanup is a cosmetic concern. A follow-up commit can delete them, but it is not part of the migration itself.

** Rollback strategy

If at any point during the migration a step breaks and you need to roll back:

1. =git stash= or =git checkout= to the last green commit.
2. The =flake.nix= at that commit is still the auto-generated one from =flake-file=.
3. =npins/sources.json=, =follows.nix=, and =default.nix= are untracked (or in their own commits) and can be discarded without affecting the flake.

The migration is intentionally additive until step 7 — every step before that can be reverted by deleting the new files. After step 7, the rollback involves restoring the auto-generated =flake.nix= from git history and undoing the shim replacement.

* Reinstall                                                                :reinstall:

This section is the companion to [[#playbook][Playbook]]: it walks a fresh-machine install end-to-end. Use it when you are bringing Lunatix up on new hardware, on a new disk, or rebuilding after disk failure. The flow assumes the migration to no-flake is already complete.

** Two-track strategy

You have two paths:

- *Track A: dry-run on QEMU first* — boot the config in a VM, validate, then re-run on hardware. Cheap iteration. Recommended for new hardware.
- *Track B: straight to hardware* — flash ISO to USB, boot, run =nixos-install=. Faster if the hardware is known-good and matches =modules/disko/latitude3250.nix=.

[[#track-a-qemu-dry-run][Track A]] is below. [[#track-b-hardware-install][Track B]] follows.

** Prerequisites (both tracks)

You need on the machine you are installing from:

- A working =nix= with experimental features enabled:
  #+BEGIN_SRC sh
  mkdir -p ~/.config/nix
  echo "experimental-features = nix-command flakes" >> ~/.config/nix/nix.conf
  #+END_SRC
- =npins= (see [[#step-1--install-npins-one-time][step 1]])
- =git= with SSH access to =github.com/quocjq/lunatix= (for =agenix= secrets and the repo itself)
- ~20 GB free disk for build artefacts (the derivation tree for the full system is ~3 GB; intermediate builds take more)

** Clone the repo

#+BEGIN_SRC sh
git clone git@github.com:quocjq/lunatix.git ~/lunatix
cd ~/lunatix
git checkout worktree/migration-to-unflake   # or main, once merged
#+END_SRC

** Bootstrap pins and shell

#+BEGIN_SRC sh
npins init                                    # only on a fresh clone
npins update
#+END_SRC

Verify the inputs are resolvable:

#+BEGIN_SRC sh
nix-instantiate --eval --strict --json -E '
  let
    sources = import ./npins;
    follows = import ./follows.nix;
    with-inputs = import sources.with-inputs sources follows;
  in builtins.attrNames (with-inputs (x: x))' | head -c 200
#+END_SRC

Should print a JSON object whose keys are the 20 input names.

*** Track A: QEMU dry-run

Build the existing VM first (sanity check):

#+BEGIN_SRC sh
just build
just vm            # launches the NixOS-internal VM (system.build.vm)
#+END_SRC

Then build the standalone QEMU runner (see the [[file:../../modules/flake/qemu.nix][qemu module]]):

#+BEGIN_SRC sh
nix build .#qemu
./result/bin/qemu --help 2>&1 | head -20
#+END_SRC

Create a backing qcow2 disk:

#+BEGIN_SRC sh
qemu-img create -f qcow2 lunatix.qcow2 64G
#+END_SRC

Launch the VM with the disk attached:

#+BEGIN_SRC sh
./result/bin/qemu -drive file=lunatix.qcow2,if=virtio,format=qcow2
#+END_SRC

The VM boots into the NixOS installer ISO (or a pre-installed image — see [[#build-an-iso][Build an ISO]] below). Walk through [[#track-b-hardware-install][Track B]] inside the VM as a rehearsal.

*** Track B: hardware install

**** Build an ISO

Build a bootable ISO that runs =nixos-install= unattended:

#+BEGIN_SRC sh
nix build .#install-iso -o result-iso
ls -la result-iso/iso/*.iso
#+END_SRC

(If you have not set up the =install-iso= package yet, see =modules/flake/installer.nix= — this is a future addition. For now, use the upstream =nixos-installer= ISO and run the disko step manually.)

Flash to USB:

#+BEGIN_SRC sh
sudo dd if=result-iso/iso/lunatix-installer.iso of=/dev/sdX bs=4M status=progress conv=fsync
sync
#+END_SRC

Replace =/dev/sdX= with your USB device. Verify with =lsblk= before running.

**** Boot the target machine

1. Insert the USB.
2. Enter BIOS/UEFI.
3. Disable Secure Boot (Lunatix uses custom keys via =agenix=; unsigned boot chain).
4. Set boot order to USB first.
5. Boot.

You land in a NixOS installer shell.

**** Disko partitioning

The disko config at =modules/disko/latitude3250.nix= matches the Dell Latitude 3250 layout. If the new machine is *different*, fork that file first (see =current-state.md= for the structure).

#+BEGIN_SRC sh
sudo nix --experimental-features "nix-command flakes" run \
  github:nix-community/disko -- \
  --mode disko \
  --flake .#igloo
#+END_SRC

This wipes the target disk and creates the LUKS+btrfs layout. Verify with =lsblk= before continuing.

**** Mount and install

#+BEGIN_SRC sh
sudo mount /dev/mapper/root /mnt
sudo mkdir -p /mnt/boot
sudo mount /dev/sda1 /mnt/boot

sudo nixos-install --flake .#igloo --no-root-password
#+END_SRC

The =--no-root-password= flag is intentional: you set the user password in [[#first-boot][First boot]]. If =agenix= complains about missing secrets, see [[#secrets-agenix][Secrets (agenix)]].

**** First boot

After =nixos-install= completes:

#+BEGIN_SRC sh
sudo reboot
#+END_SRC

Remove the USB during POST. The system boots into the graphical login manager (Hyprland per =modules/lunix/hyprland/hyprland.nix=).

Login as =lunixose=. The home-manager activation runs on first login.

***** Verify checklist

After first boot, run these from the user shell:

#+BEGIN_SRC sh
# Confirm den outputs are wired
den --help 2>/dev/null || echo "den not on PATH yet — check nix profile"

# Confirm home-manager is active
home-manager --version

# Confirm agenix secrets are decrypted
ls ~/.ssh/ 2>/dev/null | head

# Confirm the user's den modules resolved
ls -la ~/.config/nix/den/ 2>/dev/null
#+END_SRC

** Secrets (agenix)

=agenix= decrypts =.age= files using host-specific keys. The host key is generated at install time and stored in =/etc/agenix/=. The user key is generated once and stored in the =agenix-rekey= input.

If you are migrating from an old machine:

#+BEGIN_SRC sh
# On the OLD machine: export the secrets
nix run .#rekey -- --to user@lunixose@new-host

# On the NEW machine: import
just secret-pull
#+END_SRC

If this is the first install (=agenix= not yet initialized):

#+BEGIN_SRC sh
just new-ssh-key          # generates ~/.ssh/id_ed25519
just rekey                # rotates secrets to the new host key
just secret*              # decrypt all .age files
#+END_SRC

** Common pitfalls

| Symptom                                                       | Likely cause                                | Fix                                                       |
|---------------------------------------------------------------+---------------------------------------------+-----------------------------------------------------------|
| =npins: command not found=                                    | =npins= not installed                       | [[#step-1--install-npins-one-time][step 1]]                                              |
| =error: input 'nixpkgs-lib' has no URL=                       | =follows.nix= missing an entry              | [[#step-4--generate-followsnix][step 4]]                                              |
| =error: flake 'git@github.com:...' requires SSH access=       | SSH key not on the github account           | =ssh-add= or add =IdentityFile= to =~/.ssh/config=         |
| =agenix: file 'secrets/foo.age' not found=                    | Secrets not rekeyed to new host             | [[#secrets-agenix][Secrets (agenix)]]                                       |
| Boot hangs at "=Switching root="                              | =disko= layout wrong                        | Re-check =modules/disko/latitude3250.nix= for new hardware |
| =nixos-install: cannot find .#igloo=                          | =default.nix= not yet created (pre-step 5)   | Run [[#playbook][Playbook]] through step 5 first                          |
| Wi-Fi adapter not recognised                                  | Missing firmware for the chipset            | Add =hardware.enableRedistributableFirmware= or the firmware package to =latitude3250= |

** Rehearsal mode (read-only)

If you just want to validate the config without writing to disk:

#+BEGIN_SRC sh
just build                  # build the system derivation
just vm                     # launch NixOS-internal VM (no disk writes)

# or, standalone QEMU with a throwaway disk:
nix build .#qemu
qemu-img create -f qcow2 /tmp/lunatix-test.qcow2 32G
./result/bin/qemu -drive file=/tmp/lunatix-test.qcow2,if=virtio,format=qcow2 -m 4G -smp 4
#+END_SRC

The QEMU VM shares the host's =/nix/store= via the read-only bind mount that NixOS's =system.build.vm= sets up. Packages installed inside the VM land in a copy-on-write overlay and do not pollute the host store.

** Recovery: roll back after a bad install

If a new install fails to boot, the previous generation is still on the disk (assuming the disk was not wiped):

1. At GRUB, choose an earlier generation.
2. If GRUB is unreachable, boot the USB installer, =chroot= into the system, and run =nixos-rebuild switch --rollback=.
3. If the disk is unbootable, re-flash and re-run [[#disko-partitioning][Disko partitioning]] + [[#mount-and-install][Mount and install]].

* Known limitations (as of August 2026)

Captured while attempting an end-to-end migration in =/home/lunixose/Proj/lunatix-unflaked/= (branch =no-flake-applied=). These are real issues, not deal-breakers — flag them before you commit to the migration.

** 1. =follows.nix= syntax is easy to get wrong

=with-inputs= interprets each follows entry as a *spec* with only =inputs.Y.follows = "Z"= (or =follows = "Z"=) keys. The natural-looking shape ={ Y = "Z"; }= is NOT a spec — =with-inputs= returns it as a raw value, and your follows are silently lost. Symptom: =inputs.flake-parts.lib= is missing because =flake-parts.nixpkgs-lib= gets resolved as a raw string instead of an input. Always use the ={ inputs.Y.follows = "Z"; }= shape (or the equivalent =inputs = { Y.follows = "Z"; };=). See [[#step-4--generate-followsnix][step 4]] for the corrected template.

** 2. Transitive flake inputs are not auto-resolved

A real flake.lock records every transitive input (=flake-parts_2=, =nixpkgs_2=, =systems=, =nur=, ~67 extra pins for this config). =npins= only tracks direct pins, and =with-inputs= does not auto-fetch transitive flake inputs. Symptom: builds fail inside a transitive flake's =outputs= function with errors like =cannot coerce a set to a string= or =attribute 'X' missing=. Workaround: pre-populate =npins/sources.json= with all transitive pins lifted from the original =flake.lock= (script that does this for =lunatix= is in the =no-flake-applied= branch's commit history). For configs that pin simpler flake trees (vix-style), this isn't needed.

** 3. =with-inputs= does not expose =self= on flake inputs

In flake mode, every input has a magic =self= attribute that points back to the flake's =outputs=. =with-inputs= does NOT replicate this on resolved flake inputs (=inputs.X.self= is missing for all X). Symptom: flakes whose =outputs= function does =pkgs.callPackages self mergedArgs= or otherwise references =self= as a package set break. Affected in =lunatix=: =nix-doom-emacs-unstraightened= (line 78 of its =flake.nix=). Workarounds: (a) pin a fork of =with-inputs= that exposes =self= on flake-resolved entries, (b) vendor the affected flake as a non-flake source (=flake = false;= in npins), or (c) patch the upstream flake. The vix repo works because its flakes don't use =self= in their outputs functions.

** 4. =flake.nix= shim interacts oddly with =nix flake lock=

Running =nix flake lock= against the two-line shim (={ outputs = _: import ./.; }=) produces a =flake.lock= with only the root node. Transitive deps are resolved at evaluation time against the underlying =npins/sources.json=, so the lock file is no longer a full record of what will actually be built. If you keep =flake.lock= for tooling that reads it, treat it as informational only — =npins/sources.json= is the real source of truth.

** 5. Cold-cache evaluation can be slower, not faster

The "unflake is faster" claim circulating online usually refers to =flake-parts= evaluation overhead on warm caches, not full system builds. The first build after switching to no-flake was observably slower for =lunatix= because every transitive flake input had to be re-fetched individually rather than from the pre-locked =flake.lock= tree. Warm-cache rebuilds are roughly equivalent.
